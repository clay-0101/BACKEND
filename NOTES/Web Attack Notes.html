The server we protect
One Express + MongoDB API used in every example below
The one rule

Everything inside req.body, req.query, req.params, req.cookies and req.headers comes from the client. The client can be your React app, Postman, or a script someone wrote to attack you. Treat every value as untrusted until you have checked it.

All examples use one small API: users can sign up, log in, write posts and comment. The stack is the one you already use: Express, Mongoose, JWT access token in memory, refresh token in a cookie, bcrypt for passwords. Validation is done with express-validator.

Terminal 
npm install express mongoose express-validator helmet express-rate-limit cookie-parser csrf-csrf jsonwebtoken bcryptjs

The validate middleware

express-validator rules only collect errors. This tiny middleware reads them and stops the request with 400 before your controller runs. Every route in these notes uses it.

src/middlewares/validate.js 
const { validationResult } = require('express-validator');

function validate(req, res, next) {
  const errors = validationResult(req);
  if (!errors.isEmpty()) {
    return res.status(400).json({ errors: errors.array() });
  }
  next();
}

module.exports = validate;

01
Cross-Site Scripting (XSS)
User text is shown on the page and the browser runs it as code
What it is

Your server stores or returns text that a user typed. If that text contains HTML like a <script> tag, and the frontend puts it on the page as HTML, the browser runs it as JavaScript.

That script runs inside your site, with the logged-in user's access. It can read the page, call your API as that user, and send data out.

Three kinds of XSS

TypeWhere the script livesCommon spot
StoredSaved in your database, shown to every visitorComments, bios, post titles
ReflectedSent in the request, printed back in the responseA page that prints ?search= back
DOM-basedFrontend JS puts URL or input into innerHTMLReading location.hash into the page

How stored XSS flows

Where the bug is

Two mistakes work together. The server saves the text as-is, and the frontend renders it as HTML.

src/routes/post.routes.js
vulnerable
router.post('/:postId/comments', auth, async (req, res) => {
  const comment = await Comment.create({
    post: req.params.postId,
    author: req.user.id,
    text: req.body.text,            // saved exactly as the client sent it
  });
  res.status(201).json(comment);
});
CommentItem.jsx (React)
vulnerable
function CommentItem({ comment }) {
  // turns the text into real HTML, so a script tag inside becomes code
  return <p dangerouslySetInnerHTML={{ __html: comment.text }} />;
}

How to stop it

Step 1Validate and escape the input

.escape() replaces <, >, &, ' and " with HTML entities. After that, a browser shows the characters as plain text instead of running them.

src/routes/post.routes.js
fixed
const { body, param, matchedData } = require('express-validator');
const validate = require('../middlewares/validate');

const commentRules = [
  param('postId').isMongoId().withMessage('Invalid post id'),
  body('text')
    .isString().withMessage('Comment must be text')
    .trim()
    .isLength({ min: 1, max: 500 }).withMessage('Comment must be 1 to 500 characters')
    .escape(),                      // < > & ' " become HTML entities
];

router.post('/:postId/comments', auth, commentRules, validate, async (req, res) => {
  const { postId, text } = matchedData(req);   // only fields that passed the rules
  const comment = await Comment.create({ post: postId, author: req.user.id, text });
  res.status(201).json(comment);
});

Step 2Render user text as text in React

Step 3Add a Content-Security-Policy with helmet

      

        

          src/app.js
          
fixed

        

        
const helmet = require('helmet');

app.use(helmet());   // sets Content-Security-Policy, HSTS, X-Content-Type-Options and more

      

      
helmet's default policy only allows scripts from your own domain and blocks inline event handlers. So even if a script tag slips through, the browser refuses to run it. This is your second wall, not your first.


      

        
⚠️

        
The CSP header must be on the response that serves your HTML page. If Express only sends JSON and your React build is served by NGINX or a CDN, set the CSP there too. Also remember: the refresh token in an httpOnly cookie can't be read by a script, but an injected script can still call your API as the user while the tab is open. Fixing XSS itself matters most.

02

        

          
Cross-Site Request Forgery (CSRF)

          
Another site makes the victim's browser send a request to your API

        

      


      

        
What it is

        
A browser attaches your site's cookies to every request sent to your domain, even when that request was started by a page on a different website.

        
CSRF uses this. A page the attacker controls makes the victim's browser send a request to your API. The cookie goes along automatically, so your server thinks the user did it.

      


      

        
💡

        
CSRF only works with cookies. If your access token lives in memory and is sent in the Authorization header, another site cannot add that header, so those routes are safe from CSRF. But many projects keep the JWT in a cookie with res.cookie('token', ...), and your refresh token is always a cookie. That is where CSRF hits.

      


      
How CSRF flows

      


      
Where the bug is

      

        

          auth controller + middleware + route
          
vulnerable

        

        
// login controller
res.cookie('token', token);                 // no sameSite, no httpOnly, no secure

// src/middlewares/auth.js
const token = req.cookies.token;            // any request carrying the cookie is trusted

// src/routes/user.routes.js
router.post('/me/email', auth, async (req, res) => {
  await User.findByIdAndUpdate(req.user.id, { email: req.body.email });
  res.json({ message: 'Email updated' });
});

      


      
How to stop it


      
Step 1Set safe cookie options

      

        

          login controller
          
fixed

        

        
res.cookie('token', token, {
  httpOnly: true,               // JavaScript can't read it
  secure: true,                 // only sent over HTTPS
  sameSite: 'strict',           // not sent on requests started by other sites
  maxAge: 15 * 60 * 1000,       // 15 minutes
});

      

      

        

          
OptionValue usedWhat it does

          
            
httpOnlytrueHides the cookie from document.cookie. Protects against XSS stealing it.

            
securetrueCookie is only sent over HTTPS, never plain HTTP.

            
sameSite'strict'Browser never sends the cookie on a request started by another site. This is the main CSRF fix.

            
sameSite'lax'Sent when the user clicks a link to your site (GET), not on cross-site POST, PUT or DELETE.

            
sameSite'none'Always sent, from any site. Needs secure: true. Avoid for auth cookies.

            
maxAge900000Cookie expires after 15 minutes (value is in milliseconds).

          
        

      

      

        
💡

        
"Site" means the main domain. app.yourapp.com and api.yourapp.com are the same site, so sameSite: 'strict' still works when your React app and API sit on different subdomains.

      


      
Step 2Add a CSRF token with csrf-csrf

      
For cookie-based auth, add a second check. The server gives the frontend a CSRF token. The frontend sends it back in the x-csrf-token header on every POST, PUT, PATCH and DELETE. Another site can't read that token, so it can't send it.

      

        

          src/app.js
          
fixed

        

        
const cookieParser = require('cookie-parser');
const { doubleCsrf } = require('csrf-csrf');

app.use(cookieParser());        // must come before doubleCsrfProtection

const { generateCsrfToken, doubleCsrfProtection } = doubleCsrf({
  getSecret: () => process.env.CSRF_SECRET,
  getSessionIdentifier: (req) => req.cookies.token ?? '',   // ties the CSRF token to this login
  cookieName: 'x-csrf-token',   // use '__Host-x-csrf-token' in production (needs HTTPS)
  cookieOptions: { sameSite: 'strict', secure: true },
});

// the frontend calls this once and keeps the token
app.get('/api/csrf-token', (req, res) => {
  res.json({ csrfToken: generateCsrfToken(req, res) });
});

// every route registered after this line needs a valid x-csrf-token header
app.use(doubleCsrfProtection);

app.use('/api/users', require('./routes/user.routes'));

      

      

        

          frontend · api.js (axios)
          

        

        
const api = axios.create({ baseURL: 'https://api.yourapp.com', withCredentials: true });

const { data } = await api.get('/api/csrf-token');
api.defaults.headers.common['x-csrf-token'] = data.csrfToken;   // sent on every request now

          src/routes/user.routes.js

CORS does not stop CSRF. CORS only decides whether another site can read your response. A form POST from another site is still sent, the cookie still goes along, and your server still runs the update. Use sameSite cookies and CSRF tokens.

03

        

          
NoSQL Injection

          
An object arrives where your query expected a string

        

      


      

        
What it is

        
express.json() turns the request body into a JavaScript object. A field you expect to be a string can arrive as an object instead.

        
If that object contains a MongoDB query operator and you pass it straight into findOne(), MongoDB reads it as a condition, not a value. The meaning of your query changes, for example from "this exact token" to "any token".

      


      
How NoSQL injection flows

      


      
Where the bug is

      

        

          src/routes/auth.routes.js
          
vulnerable

        

        
router.post('/reset-password', async (req, res) => {
  const { token, newPassword } = req.body;            // no type check at all

  const user = await User.findOne({
    resetToken: token,                                // could be an object, not a string
    resetTokenExpiry: { $gt: Date.now() },
  });
  if (!user) return res.status(400).json({ message: 'Invalid or expired link' });

  user.password = await bcrypt.hash(newPassword, 12);
  user.resetToken = undefined;
  await user.save();
  res.json({ message: 'Password updated' });
});

      


      
How to stop it


      
Step 1Check the type with express-validator

      
The reset token is created with crypto.randomBytes(32).toString('hex'), so a real one is always a 64-character hex string. Say exactly that.

      

        

          src/routes/auth.routes.js
          
fixed

        

        
const { body } = require('express-validator');

const resetRules = [
  body('token')
    .isString().withMessage('Token must be a string')     // an object fails right here
    .isLength({ min: 64, max: 64 }).withMessage('Invalid token')
    .isHexadecimal().withMessage('Invalid token'),
  body('newPassword')
    .isString()
    .isStrongPassword().withMessage('Use 8+ characters with upper, lower, number and symbol'),
];

router.post('/reset-password', resetRules, validate, resetPassword);

      


      
Step 2Use only validated data in the controller

      

        

          src/controllers/auth.controller.js
          
fixed

        

        
const mongoose = require('mongoose');
const { matchedData } = require('express-validator');

async function resetPassword(req, res) {
  const { token, newPassword } = matchedData(req);    // only fields that passed the rules

  const user = await User.findOne({
    resetToken: token,
    resetTokenExpiry: mongoose.trusted({ $gt: Date.now() }),   // our own operator, see step 3
  });
  if (!user) return res.status(400).json({ message: 'Invalid or expired link' });

  user.password = await bcrypt.hash(newPassword, 12);
  user.resetToken = undefined;
  user.resetTokenExpiry = undefined;
  await user.save();
  res.json({ message: 'Password updated' });
}

      


      
Step 3Turn on Mongoose's safety net

      

        

          src/app.js
          
fixed

        

        
// once, before any query runs
mongoose.set('sanitizeFilter', true);

      

      
With sanitizeFilter on, if an operator object still slips into a filter, Mongoose wraps it so MongoDB compares it as a plain value. Your own operators like $gt also get wrapped, so mark them with mongoose.trusted() as in step 2.


      

        
⚠️

        
Never pass the whole req.body into Mongoose. User.findByIdAndUpdate(id, req.body) lets a user send any field, including role: 'admin'. Pick fields with matchedData(req) instead.

      

      

        
💡

        
Using Express 5? The old express-mongo-sanitize package throws an error there, because req.query became read-only. Express 5's default query parser also no longer builds nested objects from the URL. JSON bodies can still carry objects, which is why the type check in step 1 is your main defense.

      


      

        
Quick check · NoSQL injection

        
Which express-validator rule stops an object from reaching your query where a string was expected?

        

          
          
        

        

      


      

        
Quick check · NoSQL injection

        
You turned on mongoose.set('sanitizeFilter', true). Your own query uses { $gt: Date.now() }. What do you do?

Session Hijacking

          
Someone else gets a copy of a valid login token and uses it

        

      


      

        
What it is

        
After login, the server gives the browser a token (a JWT, or a session ID). From then on, whoever sends that token is the user as far as the server knows.

        
Session hijacking means an attacker gets a copy of a valid token and sends requests with it. No password needed.

      


      
How hijacking flows

      


      
How tokens leak, and the fix for each

      

        

          
LeakWhat goes wrongFix

          
            
XSSA script reads the token from localStorageAccess token in memory, refresh token in an httpOnly cookie, fix XSS (01)

            
Plain HTTPToken is readable on the network, e.g. public Wi-FiHTTPS everywhere, secure: true, HSTS from helmet

            
Token in URL?token=... lands in server logs and browser historySend tokens only in headers or cookies

            
No expiryA stolen JWT works foreverexpiresIn: '15m' + refresh token rotation

            
Fake logoutLogout only clears the frontend, server still accepts the tokenDelete the session document in MongoDB

          
        

      


      
Where the bug is

      

        

          src/routes/auth.routes.js
          
vulnerable

        

        
// login
const token = jwt.sign({ id: user._id }, process.env.JWT_SECRET);   // never expires
res.json({ token });                                               // frontend saves it in localStorage

// logout
router.post('/logout', (req, res) => {
  res.json({ message: 'Logged out' });      // the token still works on the server
});

      


      
How to stop it


      
Step 1A Session model, one document per refresh token

      

        

          src/models/session.model.js
          
fixed

        

        
const mongoose = require('mongoose');

const sessionSchema = new mongoose.Schema({
  user: { type: mongoose.Schema.Types.ObjectId, ref: 'User', required: true, index: true },
  tokenHash: { type: String, required: true, unique: true },   // sha256 of the refresh token
  usedAt: { type: Date, default: null },                       // set when the token is used once
  expiresAt: { type: Date, required: true },
});

// MongoDB deletes the document by itself when expiresAt passes
sessionSchema.index({ expiresAt: 1 }, { expireAfterSeconds: 0 });

module.exports = mongoose.model('Session', sessionSchema);

      


      
Step 2Short access token, hashed refresh token in a strict cookie

      

        

          src/utils/tokens.js
          
fixed

        

        
const crypto = require('crypto');
const jwt = require('jsonwebtoken');
const Session = require('../models/session.model');

const sha256 = (value) => crypto.createHash('sha256').update(value).digest('hex');
const WEEK = 7 * 24 * 60 * 60 * 1000;

async function issueTokens(res, user) {
  const accessToken = jwt.sign(
    { id: user._id, role: user.role },
    process.env.ACCESS_SECRET,
    { expiresIn: '15m' }                    // a stolen copy dies fast
  );

  const refreshToken = crypto.randomBytes(40).toString('hex');   // 80 hex characters
  await Session.create({
    user: user._id,
    tokenHash: sha256(refreshToken),        // store the hash, never the token itself
    expiresAt: new Date(Date.now() + WEEK),
  });

  res.cookie('refreshToken', refreshToken, {
    httpOnly: true,
    secure: true,
    sameSite: 'strict',
    path: '/api/auth',                      // sent only to /api/auth/* routes
    maxAge: WEEK,
  });

  res.json({ accessToken });                // frontend keeps it in memory, not localStorage
}

module.exports = { issueTokens, sha256 };

      


      
Step 3Rotate on every refresh and catch reused tokens

      
Each refresh token works once. If an already-used token shows up again, two people hold a copy: the real user and someone else. The server cannot tell who is who, so it ends every session of that user.

      

        

          src/routes/auth.routes.js
          
fixed

        

        
const { cookie } = require('express-validator');
const { issueTokens, sha256 } = require('../utils/tokens');

router.post(
  '/refresh',
  cookie('refreshToken').isString().isHexadecimal().isLength({ min: 80, max: 80 }),
  validate,
  async (req, res) => {
    const hash = sha256(req.cookies.refreshToken);

    // mark the token as used in one atomic step
    const session = await Session.findOneAndUpdate(
      { tokenHash: hash, usedAt: null },
      { usedAt: new Date() }
    );

    if (!session) {
      // token exists but was already used: a copy is out there
      const reused = await Session.findOne({ tokenHash: hash });
      if (reused) await Session.deleteMany({ user: reused.user });
      res.clearCookie('refreshToken', { path: '/api/auth' });
      return res.status(401).json({ message: 'Please log in again' });
    }

    if (session.expiresAt < new Date()) {
      return res.status(401).json({ message: 'Session expired' });
    }

    const user = await User.findById(session.user);
    await issueTokens(res, user);            // new access token + new refresh token
  }
);

      


      
Step 4Make logout real

      

        

          src/routes/auth.routes.js
          
fixed

        

        
router.post('/logout', async (req, res) => {
  const token = req.cookies.refreshToken;
  if (token) await Session.deleteOne({ tokenHash: sha256(token) });
  res.clearCookie('refreshToken', { path: '/api/auth' });
  res.json({ message: 'Logged out' });
});

      


      

        
💡

        
Using express-session instead of JWT? Call req.session.regenerate() right after a successful login. If you reuse the session ID that existed before login, an attacker who planted that ID can use it (this is called session fixation).

Quick check · Session hijacking

05

        

          
Brute Force

          
Guessing passwords by sending login requests again and again

        

      


      

        
What it is

        
The attacker sends login requests in a loop, each with a different password guess, until one works. A script can send thousands of guesses per minute.

        
Without limits, your server answers every single one, runs a database query and a bcrypt compare each time, and sooner or later a weak password falls.

      


      

        

          
VariantWhat the attacker triesWhat stops it

          
            
Brute forceMany passwords against one accountPer-IP rate limit + account lock

            
Password sprayingOne common password against many accountsPer-IP rate limit + strong password rules

            
Credential stuffingEmail + password pairs leaked from other websitesRate limit, account lock, 2FA

          
        

      


      
How brute force flows

      


      
Where the bug is

      

        

          src/routes/auth.routes.js
          
vulnerable

        

        
// no limit, and the errors tell the attacker which part was wrong
router.post('/login', async (req, res) => {
  const user = await User.findOne({ email: req.body.email });
  if (!user) return res.status(404).json({ message: 'No account with this email' });

  const ok = await bcrypt.compare(req.body.password, user.password);
  if (!ok) return res.status(401).json({ message: 'Wrong password' });

  await issueTokens(res, user);
});

      


      
How to stop it


      
Step 1Validate login and register input

      

        

          src/routes/auth.routes.js
          
fixed

        

        
const { body } = require('express-validator');

const loginRules = [
  body('email').isEmail().withMessage('Enter a valid email').normalizeEmail(),
  body('password').isString().isLength({ min: 8, max: 72 }),   // bcrypt only reads 72 bytes
];

const registerRules = [
  body('email').isEmail().normalizeEmail(),
  body('password')
    .isString()
    .isStrongPassword().withMessage('Use 8+ characters with upper, lower, number and symbol'),
];

      


      
Step 2Rate limit the login route

      

        

          src/routes/auth.routes.js
          
fixed

        

        
const { rateLimit } = require('express-rate-limit');

const loginLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,         // 15 minutes
  limit: 5,                         // 5 failed attempts per IP per window
  skipSuccessfulRequests: true,     // a correct login does not count
  standardHeaders: 'draft-8',
  legacyHeaders: false,
  message: { message: 'Too many login attempts. Try again in 15 minutes.' },
});

router.post('/login', loginLimiter, loginRules, validate, login);

      

      

        

          
OptionValue usedWhat it does

          
            
windowMs900000Length of the counting window in milliseconds (15 minutes).

            
limit5Requests allowed per IP in one window. Request 6 gets 429 Too Many Requests.

            
skipSuccessfulRequeststrueOnly failed logins (status 400 and up) are counted.

            
standardHeaders'draft-8'Sends the standard RateLimit headers so clients know when to retry.

            
legacyHeadersfalseTurns off the old X-RateLimit-* headers.

            
message{ message }JSON body sent with the 429 response.

          
        

      


      
Step 3Lock the account, whatever the IP

      
An attacker can switch IPs, so the per-IP limit is not enough on its own. Count failures on the user document too.

      

        

          src/models/user.model.js (extra fields)
          

        

        
failedLogins: { type: Number, default: 0 },
lockUntil: { type: Date },

      

      

        

          src/controllers/auth.controller.js
          
fixed

        

        
async function login(req, res) {
  const { email, password } = matchedData(req);
  const user = await User.findOne({ email }).select('+password');

  // same answer for "no such email" and "wrong password"
  const invalid = () => res.status(401).json({ message: 'Invalid email or password' });
  if (!user) return invalid();

  if (user.lockUntil && user.lockUntil > Date.now()) {
    return res.status(429).json({ message: 'Too many attempts. Try again later.' });
  }

  const ok = await bcrypt.compare(password, user.password);
  if (!ok) {
    user.failedLogins += 1;
    if (user.failedLogins >= 10) {
      user.lockUntil = new Date(Date.now() + 15 * 60 * 1000);   // lock for 15 minutes
      user.failedLogins = 0;
    }
    await user.save();
    return invalid();
  }

  user.failedLogins = 0;
  user.lockUntil = undefined;
  await user.save();
  await issueTokens(res, user);
}

      


      

        
⚠️

        
Behind a load balancer? Set app.set('trust proxy', 1). Without it, every request looks like it comes from the load balancer's IP, so all your users share one counter and get blocked together. With more than one pod, use a shared store like rate-limit-redis so every pod sees the same counts.

06

        

          
DoS & DDoS

          
Keeping the server so busy that real users can't use it

        

      


      

        
What it is

        
Denial of Service (DoS): make the server so busy that it can't answer real users. Nothing is stolen. The goal is to take the service down.

        
It comes in two shapes: too many requests, or a few very expensive requests (a huge JSON body, ?limit=1000000, a slow query without an index). DDoS is the same thing from thousands of machines at once.

      


      

        

          
WhatDoSDDoS

          
            
SourceOne machine, one IPThousands of hacked machines (a botnet)

            
Block one IP?Works ✓Useless, there are thousands

            
Per-IP rate limit?Works ✓Each IP stays under the limit

            
Where to stop itInside ExpressAt the edge: CDN, WAF, cloud provider ✓

          
        

      


      
How DoS and DDoS flow

      


      
Where the bug is

      

        

          src/app.js + src/routes/post.routes.js
          
vulnerable

        

        
app.use(express.json());                     // accepts bodies up to the default 100kb, no rate limit

router.get('/', async (req, res) => {
  const limit = Number(req.query.limit);     // ?limit=1000000 is accepted
  const posts = await Post.find().limit(limit);
  res.json(posts);
});

      


      
How to stop it


      
Step 1Small body limit

      

        

          src/app.js
          
fixed

        

        
app.use(express.json({ limit: '10kb' }));                           // bigger bodies get 413
app.use(express.urlencoded({ extended: false, limit: '10kb' }));

      


      
Step 2A global rate limit for the API

      

        

          src/app.js
          
fixed

        

        
const { rateLimit } = require('express-rate-limit');

app.set('trust proxy', 1);                   // real client IP from the load balancer

app.use('/api', rateLimit({
  windowMs: 60 * 1000,                       // 1 minute
  limit: 100,                                // 100 requests per IP per minute
  standardHeaders: 'draft-8',
  legacyHeaders: false,
}));

      


      
Step 3Cap expensive queries with express-validator

      

        

          src/routes/post.routes.js
          
fixed

        

        
const { query, matchedData } = require('express-validator');

const listRules = [
  query('page').optional().isInt({ min: 1, max: 1000 }).toInt(),
  query('limit').optional().isInt({ min: 1, max: 50 }).toInt(),   // never more than 50
];

router.get('/', listRules, validate, async (req, res) => {
  const { page = 1, limit = 20 } = matchedData(req);

  const posts = await Post.find()
    .sort({ createdAt: -1 })                // make sure createdAt has an index
    .skip((page - 1) * limit)
    .limit(limit)
    .maxTimeMS(2000)                        // MongoDB stops the query after 2 seconds
    .lean();

  res.json(posts);
});

      


      
Step 4For DDoS, stop it before it reaches Express

      
No Express middleware can survive traffic from thousands of IPs on its own, because the requests still reach your server and use its network and CPU. Protection has to sit in front of your app.

      

        Traffic from 20,000 IPs hits your domain

            ↓

        CDN / WAF (Cloudflare, AWS Shield + AWS WAF) drops known-bad and excess traffic

            ↓

        Load balancer spreads what is left across pods

            ↓

        Kubernetes HPA adds pods when CPU climbs

            ↓

        Express: body limit + rate limit (Redis store) + capped queries ✅

07

        

          
Slow Request Attack

          
Sending the request body so slowly that connections stay stuck

        

      


      

        
What it is

        
A normal request arrives in milliseconds. In a slow request attack, the client sends valid headers that promise a body, then sends that body extremely slowly, just fast enough that the connection never looks dead.

        
The server keeps the connection open, waiting for the rest. Repeat this on many connections and the server runs out of room for real users, while almost no traffic shows up on your graphs.

      


      
How a slow request attack flows

      


      

        
⚠️

        
express-validator can't help here. Validation runs after the whole body has arrived. This attack happens before that, while the body is still coming in. It is stopped at the connection level, with timeouts.

      


      
Where the bug is

      
Since Node 18, server.requestTimeout defaults to 5 minutes. That means a connection can be held for up to 5 minutes before Node closes it. Before Node 18 there was no limit at all.

      

        

          src/server.js
          
vulnerable

        

        
const app = require('./app');

app.listen(process.env.PORT || 3000);      // default timeouts: a stuck request may live for minutes

      


      
How to stop it


      
Step 1Set Node's connection timeouts

      

        

          src/server.js
          
fixed

        

        
const app = require('./app');

const server = app.listen(process.env.PORT || 3000, () => {
  console.log('API running');
});

server.headersTimeout = 10_000;      // all headers within 10s of the first byte
server.requestTimeout = 30_000;      // headers + body within 30s, or the connection is closed
server.keepAliveTimeout = 5_000;     // close idle keep-alive connections after 5s

      

      

        

          
SettingNode defaultWhat it does

          
            
requestTimeout300000 (5 min)Deadline for the whole request, headers and body. This is the one that stops slow bodies.

            
headersTimeout60000 (60 s)Deadline for the headers only. Stops Slowloris (section 08).

            
keepAliveTimeout5000 (5 s)How long an idle connection stays open after a response.

          
        

      


      
Step 2Keep the body limit from section 06

      
express.json({ limit: '10kb' }) rejects a body as soon as it grows past 10 KB, so the attacker can't keep a connection busy with a huge upload either.


      
Step 3Let a reverse proxy face slow clients

      
In production, NGINX or a load balancer sits in front of Node. It reads the whole request first and only then forwards it to Express. Slow clients get stuck at the proxy, which is built to hold many connections cheaply.

      

        

          nginx.conf (inside the server block)
          

        

        
client_header_timeout 10s;   # headers must arrive within 10s
client_body_timeout   10s;   # max wait between two pieces of the body
client_max_body_size  1m;    # refuse bodies above 1 MB

      


      

        
💡

        
Running behind an AWS ALB? The ALB faces the slow client, not Node. Then set server.keepAliveTimeout higher than the ALB idle timeout (60 s by default), for example 65_000. If Node closes idle connections before the ALB does, you get random 502 errors.

08

        

          
Slowloris

          
Opening many connections whose headers never finish

        

      


      

        
What it is

        
HTTP headers end with one empty line. Until that line arrives, the server can't start handling the request, so it keeps waiting.

        
Slowloris opens many connections and sends only part of the headers on each. Every so often it adds one more header line, so the connection never goes idle. It is a slow request attack aimed at the headers instead of the body.

      


      
How Slowloris flows

      


      
Flood vs slow body vs Slowloris

      

        

          
WhatFlood (DoS)Slow body (07)Slowloris (08)

          
            
What is slowNothing, just a lot of requestsThe bodyThe headers

            
Bandwidth usedHighVery lowVery low

            
On your graphsA clear traffic spikeA few slow uploadsA few slow clients

            
Stopped byRate limit, WAFrequestTimeout, client_body_timeoutheadersTimeout, client_header_timeout

          
        

      


      

        
Why an idle timeout is not enough

        
An idle timeout (server.timeout) resets every time a byte arrives. Slowloris sends a byte just before it would fire, so it never fires. server.headersTimeout counts the total time from the first byte, so the trick stops working.

      


      
How to stop it


      
Step 1Set headersTimeout

      

        

          src/server.js
          
fixed

        

        
server.headersTimeout = 10_000;   // headers not done 10s after the first byte: Node sends 408 and closes
server.requestTimeout = 30_000;   // keep this larger than headersTimeout

      


      
Step 2Proxy timeout in front

      
The same NGINX setting from section 07, client_header_timeout 10s, stops Slowloris before it reaches Node. Managed load balancers like AWS ALB also wait for complete headers before they forward anything.


      
VerifyPrint the values your server is really using

      

        

          src/server.js
          

        

        
console.log({
  headersTimeout: server.headersTimeout,       // expect 10000
  requestTimeout: server.requestTimeout,       // expect 30000
  keepAliveTimeout: server.keepAliveTimeout,   // expect 5000
});

      


      

        
💡

        
Why old servers suffered most. Slowloris was famous against servers that gave every connection its own thread, like Apache in prefork mode: a few hundred stuck connections used up every thread. Node does not block a thread per connection, but each open socket still costs memory and a file descriptor, so you still need the timeout.

Order matters. Security headers and rate limits run first so bad traffic is dropped early. Body parsing comes next, then cookies and CSRF, then your routes.

const express = require('express');
const helmet = require('helmet');
const mongoose = require('mongoose');
const cookieParser = require('cookie-parser');

mongoose.set('sanitizeFilter', true);           // 03 NoSQL injection safety net

const app = express();
app.set('trust proxy', 1);                       // real client IP behind ALB / NGINX

app.use(helmet());                               // 01 XSS: CSP + security headers
app.use('/api', rateLimit({                      // 06 DoS: 100 req / min / IP
  windowMs: 60 * 1000,
  limit: 100,
  standardHeaders: 'draft-8',
  legacyHeaders: false,
}));
app.use(express.json({ limit: '10kb' }));        // 06 DoS: small bodies only
app.use(cookieParser());

// 02 CSRF: add doubleCsrfProtection here if your auth uses cookies

app.use('/api/auth', require('./routes/auth.routes'));    // 04 + 05: rotation, login limiter
app.use('/api/posts', require('./routes/post.routes'));   // 01 + 06: escaped comments, capped lists
app.use('/api/users', require('./routes/user.routes'));   // 02: validated email change

module.exports = app;
