The rotten biryani problem
Why a smart LLM still fails at a simple support chat

Reality check against the policy

  • ✗"Refund to your bank". Policy §4.3 says refunds go to the Khaana Wallet, and only after verification.
  • ✗"₹500 coupon". Policy §5.1 caps goodwill coupons at ₹100.
  • ✗No photo asked for. Policy §4.2 requires one before any refund.
2,000 chats like this a day × ₹500 = ₹10 lakh a day in coupons that should never exist.

Why did that happen?

Think of the LLM as a brilliant new support agent on their first day. They speak well, they understand the customer, but nobody has handed them the company handbook. Ask them a policy question and they'll improvise something that sounds helpful.

Key Concept · Three gaps every LLM has
  • Knowledge cutoff. It learned from data up to a certain date. Anything after that date, it has never seen.
  • No private data. Khaana's refund policy, coupon rules and internal SOPs were never in its training data. They live on Khaana's servers.
  • Confident guessing. When it doesn't know, it rarely says "I don't know". It writes the most likely-sounding answer. That's a hallucination.

So today's real question is this: how do we give the LLM the right company knowledge at the exact moment a question arrives?

What goes wrong

Cost

You pay for all 122K tokens on every message, even though 99% of it has nothing to do with the question.

Latency

The model must read the whole prompt before it writes a word. Bigger prompt, slower first reply.

Context limit

Add one more document and it doesn't fit. Real companies have thousands of documents, not five.

Lost in the middle

The one clause that matters is buried among 191 pages, and models miss more facts in the middle of long prompts.

Stale rules

Policies change every week. Someone has to keep pasting the latest version into the prompt, by hand.

Access control

Internal rules, like the fraud check in §6.2, are now inside the prompt. One clever question could get them shown to a customer.

Interview favourite · "Context windows are 1M tokens now. Is RAG dead?"

No. A bigger window means more fits, but every other problem stays:

  • Cost and latency grow with every token you send, on every call.
  • Accuracy still drops when the key fact is buried in a huge prompt.
  • Scale. A company knowledge base can run to millions of tokens, more than any window.
  • Freshness and access. RAG fetches the latest version of only the documents this user is allowed to see.
  • Prompt caching lowers the cost of repeating a fixed prefix, but it doesn't fix accuracy, access control, or a knowledge base bigger than the window.

In practice teams combine both: a bigger window lets RAG send more chunks, and bigger ones.

So what do we actually want?

03
Embeddings and vectors
How a computer can tell that "rotten" and "spoiled" mean the same thing

To search by meaning, we need to turn meaning into numbers. Start with something simple: a measuring scale that runs from 0 to 1. We'll measure animals on it and place each one where its number lands.

Drag to rotate
3scales needed
Key Concept

An embedding is a list of numbers that places a piece of text (a word, a sentence, a whole chunk) at a point in this kind of space. That list of numbers is a vector. The embedding model is trained so that texts with similar meaning land near each other.

💡

In our animal story every scale had a name: "dog-like", "lives in water", "flies". Real embedding dimensions have no names. The model learns them during training, and meaning is spread across all of them together. If an interviewer asks "what does dimension 42 mean?", the right answer is that no single dimension means anything readable on its own.

From animals to sentences

The same idea works for whole sentences. Every policy paragraph becomes a point. Similar rules cluster together. When a customer's question arrives, we turn it into a point too, and look at what's closest.

nearest 1 · §4.1Spoiled, stale or unfit items can be reported within 2 hours of delivery.
nearest 2 · §4.3After photo verification, the full item value goes to the Khaana Wallet within 2 hours.
nearest 3 · §3.1Cancelled orders are refunded to the original payment method in 5 to 7 working days.

Real embedding models

Our story needed 3 scales for 7 animals. Real models need hundreds or thousands, because they place every word and sentence in every language. The number of dimensions is fixed per model.

ModelDimensionsNotes
mistral-embed1024Mistral's embedding model. What we'll use in class.

text-embedding-3-large3072OpenAI, higher quality, bigger vectors to store.

⚠️

Use the same embedding model for your documents and your questions. Vectors from different models live in different spaces. Comparing them is like measuring one thing in centimetres and the other in kilograms.

Measuring "near": cosine similarity

Each vector is an arrow from the origin. To compare two texts we look at the angle between their arrows. Same direction means same meaning. Drag the slider.

0.87
very similar

A = "spoiled food refund"
B = "rotten food, money back"

cosine.js
// cos(θ) = (A · B) / (|A| × |B|)
function cosine(a, b) {
  let dot = 0, lenA = 0, lenB = 0;
  for (let i = 0; i < a.length; i++) {
    dot  += a[i] * b[i];
    lenA += a[i] * a[i];
    lenB += b[i] * b[i];
  }
  return dot / (Math.sqrt(lenA) * Math.sqrt(lenB));
}

cosine([1, 0], [1, 0]);   // 1   → same direction
cosine([1, 0], [0, 1]);   // 0   → unrelated
cosine([1, 0], [-1, 0]);  // -1  → opposite
💡

With real text embeddings most scores land between 0 and 1, and you rarely see negatives. The ranking matters more than the raw number. A 0.71 is only "good" if it beats the other chunks.

Load: one Document per page

A loader reads the PDF and gives back plain text plus metadata (which file, which page). Keep the metadata. It's how the bot will cite its sources later.

{ pageContent: "4. Food Quality Complaints\n4.1 If an item is spoiled, stale…", metadata: { source: "refund-policy.pdf", loc: { pageNumber: 12 } } }
Chunk: 191 pages → about 600 pieces of ~800 characters

Small enough to be about one thing, big enough to make sense on its own. Section 05 is all about how to cut well.

chunk 42 · "4.3 After photo verification…" → mistral-embed → [ 0.0213, -0.1132, 0.0871, 0.0042, … ]

600 chunks means 600 embedding calls (batched). You pay for this once, not on every question.

Store: text + vector + metadata, side by side

We'll use MongoDB Atlas, since you already know Mongo. A vector index on the embedding field makes "find the nearest vectors" fast.

numDimensions must match the embedding model. mistral-embed gives 1,024 numbers, so the index says 1024. Switch models and you must rebuild the index and re-embed everything.

Step 3 · Ingestion script
ingest.js
import "dotenv/config";
import { MongoClient } from "mongodb";
import { PDFLoader } from "@langchain/community/document_loaders/fs/pdf";
import { RecursiveCharacterTextSplitter } from "@langchain/textsplitters";
import { MistralAIEmbeddings } from "@langchain/mistralai";
import { MongoDBAtlasVectorSearch } from "@langchain/mongodb";

const client = new MongoClient(process.env.MONGODB_URI);
const collection = client.db("khaana").collection("policy_chunks");

// 1. Load: one Document per PDF page, with source + page metadata
const pages = await new PDFLoader("./refund-policy.pdf").load();

// 2. Chunk: ~800 characters, 120 characters of overlap
const splitter = new RecursiveCharacterTextSplitter({ chunkSize: 800, chunkOverlap: 120 });
const chunks = await splitter.splitDocuments(pages);

// 3 + 4. Embed every chunk and store text + vector + metadata
const embeddings = new MistralAIEmbeddings({ model: "mistral-embed" });
await MongoDBAtlasVectorSearch.fromDocuments(chunks, embeddings, {
  collection,
  indexName: "vector_index",
  textKey: "text",
  embeddingKey: "embedding",
});

console.log(`Stored ${chunks.length} chunks`);
await client.close();
Step 4 · Ask a question
ask.js
import "dotenv/config";
import { MongoClient } from "mongodb";
import { MistralAIEmbeddings, ChatMistralAI } from "@langchain/mistralai";
import { MongoDBAtlasVectorSearch } from "@langchain/mongodb";

const client = new MongoClient(process.env.MONGODB_URI);
const collection = client.db("khaana").collection("policy_chunks");

const embeddings = new MistralAIEmbeddings({ model: "mistral-embed" }); // same model as ingestion
const vectorStore = new MongoDBAtlasVectorSearch(embeddings, {
  collection,
  indexName: "vector_index",
  textKey: "text",
  embeddingKey: "embedding",
});

const question = "My biryani arrived spoiled. Can I get my money back?";

// Retrieval: embed the question + find the 3 nearest chunks
const results = await vectorStore.similaritySearchWithScore(question, 3);
results.forEach(([doc, score]) => console.log(score.toFixed(3), doc.pageContent.slice(0, 60)));

// Augmentation: put the chunks into the prompt
const context = results.map(([doc]) => doc.pageContent).join("\n---\n");

// Generation
const llm = new ChatMistralAI({ model: "mistral-small-latest", temperature: 0 });
const answer = await llm.invoke([
  ["system", `You are Khaana Express support.
Answer ONLY from the policy context below and cite section numbers.
If the answer is not in the context, say you'll connect a human agent.

Policy context:
${context}`],
  ["human", question],
]);

console.log(answer.content);
await client.close();
⚠️

The system prompt is part of RAG. Without "answer only from the context" and an escape hatch ("connect a human"), the model may ignore the chunks and fall back to guessing.

05
Chunking strategies
How you cut the documents decides what the bot can ever find

Retrieval can only return chunks that exist. If the answer is split across two chunks, or drowned inside a giant one, no embedding model can save you. That's why interviewers love this topic: bad chunking is the most common reason a RAG bot gives wrong answers.

The trade-off: too big, too small, just right

What the LLM receives

§4 Food Quality Complaints, §5 Coupons, §6 Escalation… the whole section, about 2,000 words.One vector for many topics gets blurry, so the match is weaker. The LLM also gets a lot of noise.

"…to the Khaana Wallet within 2 hours."Within 2 hours of what? A refund? The complaint window? The LLM has to guess again.

"4.3 After photo verification, the full item value is refunded to the Khaana Wallet within 2 hours."One complete idea. Sharp match, enough context.

Bonus: give every chunk its context

  
A chunk like "Refunds take 5 to 7 working days" is ambiguous on its own. Which refunds? Prepend the document and section title before embedding, so the vector carries that context too. Anthropic's write-up on Contextual Retrieval takes this further: an LLM writes a one-line summary of where each chunk sits in the document, and that line is embedded with the chunk.

  

    
Plain chunk
Refunds to the original payment method take 5 to 7 working days.

    
With a context header
Refund Policy › 4. Food Quality Complaints › Refunds to the original payment method take 5 to 7 working days.

  

  

    
💡

    
A sensible starting point: recursive splitting at around 800 to 1,000 characters with 10–20% overlap, plus a section header on each chunk. Then test with 20 real customer questions and adjust. Chunk size is tuned, not guessed.

Reranking and hybrid search

      
Vector search finds the right neighbourhood. Reranking finds the right house.

    

  


  
Vector search is fast, but it's rough. It compares two vectors that were made separately, so texts that share a vibe ("refund", "money back") can outrank the text that actually answers the question. To see why, compare the two kinds of model.


  

    

      

        

          
Bi-encoder · what vector search uses

embedding model

              
[0.02, -0.11, …]

            

            

              
Chunk §3.1"Cancelled orders: refund in 5–7 days"

              
embedding model

              
[0.03, -0.09, …]

The problem: each text was squashed into a vector on its own. The model never put "spoiled" next to "cancelled" to compare them. Both talk about refunds, so the vectors look close, and the wrong chunk wins.

Because it reads both texts at once, it notices that "spoiled food" and "cancelled order" are different situations. The output is one relevance score per pair.

          

        

        

          
So why not use a cross-encoder for everything?

          

            
Bi-encoder search
1 model run
Embed the question once, then a fast index lookup over 10,000 stored vectors. Chunk vectors were computed in advance.

            
Cross-encoder on every chunk
0 model runs
Nothing can be precomputed, because each score needs the question. Every question means scoring every chunk again.

    rerank.js · add after vector search
    
    
    import { CohereRerank } from "@langchain/cohere";

// 1. Wide net: 20 candidates from vector search
const candidates = await vectorStore.similaritySearch(question, 20);

// 2. Rerank: a cross-encoder scores each (question, chunk) pair
const reranker = new CohereRerank({ model: "rerank-v3.5", topN: 3 }); // check Cohere docs for the current model name
const top3 = await reranker.compressDocuments(candidates, question);

top3.forEach((doc) => console.log(doc.metadata.relevanceScore, doc.pageContent.slice(0, 60)));
    
  
    
  
    Other rerankers you'll hear about: BAAI bge-reranker (open source, run it yourself), Jina Reranker and Voyage rerank. They all do the same job: take a question and a list of chunks, return them re-ordered with a relevance score.
    

  
    

  
    Hybrid search: when meaning isn't enough
    
  
    Embeddings are great at meaning and bad at exact strings. Coupon codes like SORRY50, order IDs like KE-48213, product SKUs and error codes all look like noise to an embedding model. Old-school keyword search, called BM25, nails them. Hybrid search runs both and merges the two ranked lists.
    

  
    
    
    
      
    CustomerCan I use SORRY50 on order KE-48213?
    
      
    
        
    Vector search ranking
      
        
      BM25 keyword ranking
        
        
        Merged with RRF
          
      
          
      
          RRF score = 1 / (60 + rank in vector list) + 1 / (60 + rank in BM25 list)
          
    
          
  
          
  
          
    
          Key Concept · Reciprocal Rank Fusion (RRF)
          
    
          Vector scores (0 to 1) and BM25 scores (0 to 20-something) are on different scales, so you can't just add them. RRF ignores the raw scores and uses ranks: being near the top of either list earns points. The constant 60 is the usual default; it stops a single #1 from dominating. Atlas, Elasticsearch, OpenSearch and Weaviate all support some form of hybrid search.
          
  
          

  
          The full production pipeline
          
  
          
    
          Customer question
          "My biryani arrived spoiled, order KE-48213. Money back?"
          
    
          Hybrid retrieval: vector top 20 + BM25 top 20
          Meaning and exact words, in parallel. Apply metadata filters here (city, user's access level).
          
    
          Merge with RRF
          One combined list of candidates.
          
    
          Rerank with a cross-encoder, keep the top 3–5
          The expensive, accurate step, on a small list.
          
    
          Build the prompt
          Rules ("answer only from context, cite sections") + chunks + question.
          
    
          LLM answers with citations
          Grounded, cheap, and checkable.

          Interview question bank
          
      
          What gets asked about RAG right now, with answers you can say out loud
          
    
          
  
          

  
          Try answering each one yourself before you open it. A strong answer names the trade-off, not just the definition.
          
  
          

  
          Basics
          
  
          Q1What is RAG, in one or two lines?+
          
    
          At question time, we retrieve the most relevant pieces of our own data and put them in the prompt, so the LLM answers from those facts instead of from memory. It lets a general model answer questions about private, fresh data without retraining it.
          
  
          
  
          Q2What problem does RAG solve?+
          
    
          • LLMs have a knowledge cutoff and have never seen your private data.
          • When they don't know, they hallucinate confidently.
          • Pasting all your documents into the prompt is too expensive, too slow, hits the context limit, and buries the key fact in the middle.
          
    
          RAG sends only the few chunks that matter for this question.
          
  
          
  
          Q3Models have 1M-token context windows now. Is RAG dead?+
          
    
          No. Cost and latency still grow with every token on every call, accuracy still drops when a fact is buried in a huge prompt, many knowledge bases are bigger than any window, and RAG handles freshness and per-user access control. Prompt caching cuts repeat cost but not the rest. Long context and RAG work together: a bigger window lets you send more retrieved chunks, and bigger ones.
          
  
          

  
          Embeddings
          
  
          Q4What is an embedding? What does each dimension mean?+
          
    
          A fixed-length list of numbers (for example 1,024 for mistral-embed) that places text in a space where similar meanings are close together. Individual dimensions aren't human-readable. Meaning is spread across all of them, learned during training.
          
  
          
  
          Q5Cosine similarity vs dot product vs Euclidean distance?+
          
    
          • Cosine compares direction only and ignores vector length.
          • Dot product is cosine multiplied by both lengths.
          • Euclidean is straight-line distance.
          
    
          If vectors are normalised to length 1 (many embedding APIs do this), all three give the same ranking. Use whatever your embedding model recommends, and set the vector index to match.
          
  
          
  
          Q6Can you mix embeddings from two different models?+
          
    
          No. Each model has its own space, and often a different dimension count. Documents and questions must be embedded by the same model. Changing models means re-embedding the whole corpus and rebuilding the index.
          
  
          

  
          Chunking
          
  
          Q7How do you choose a chunk size?+
          
    
          It depends on the documents and the questions. Too big gives blurry vectors and noisy prompts. Too small loses context. Start with recursive splitting around 800–1,000 characters and 10–20% overlap, respect the document's structure, then measure with a set of real questions (did the right chunk come back in the top k?) and tune.
          
  
          
  
          Q8Why use overlap, and what does it cost?+
          
    
          Overlap repeats text at chunk boundaries, so a sentence cut by one chunk still appears whole in the next. The cost is duplicated storage and embedding calls, and sometimes near-duplicate chunks in the results.
          
  
          
  
          Q9Explain semantic chunking. When is it worth it?+
          
    
          Embed each sentence, compare it with the next one, and start a new chunk wherever the similarity drops below a threshold, because the topic changed. It's worth it for long prose without headings (transcripts, articles). For structured docs like policies, structure-aware splitting is cheaper and usually as good.
          
  
          
  
          Q10What is parent-child (small-to-big) retrieval?+
          
    
          Index small child chunks so search is precise, and store a link to the bigger parent section. When a child matches, send the parent to the LLM. You get sharp matching and complete context.
          
  
          

  
          Retrieval & reranking
          
  
          Q11Bi-encoder vs cross-encoder?+
          
    
          A bi-encoder embeds the question and each chunk separately, so chunk vectors can be precomputed and search is fast, but it misses fine details. A cross-encoder reads the question and a chunk together and outputs one relevance score. It's more accurate but needs a model run per pair, so it's only used to rerank a short list.
          
  
          
  
          Q12Why rerank instead of just increasing k?+
          
    
          A bigger k sends more noise and more tokens, and the right chunk can still land in the middle of a long prompt. Reranking fixes the order so the top 3–5 chunks are the best ones, keeping the prompt small and accurate.
          
  
          
  
          Q13What is hybrid search, and how do you merge the results?+
          
    
          Run vector search (meaning) and BM25 keyword search (exact terms like codes and IDs) together, then merge the lists. The common merge is Reciprocal Rank Fusion: score = Σ 1/(60 + rank) across lists. It uses ranks, so the two incompatible score scales don't matter.
          
  
          

  
          Production
          
  
          Q14Your RAG bot gives a wrong answer. How do you debug it?+
          
    
          Look at the retrieved chunks first. That splits the problem in two:
          
    
          • The right chunk wasn't retrieved: a retrieval problem. Check chunking, try hybrid search, raise k, add reranking, add metadata filters.
          • The right chunk was retrieved, but the answer is still wrong: a generation problem. Fix the prompt rules, the chunk order, or use a stronger model.
          
  
          
  
          Q15How do you evaluate a RAG system?+
          
    
          • Retrieval: build a test set of real questions with the chunk that should answer each. Measure recall@k (is it in the top k?) and MRR (how high does it rank?).
          • Generation: faithfulness (does the answer stick to the context?) and answer relevance. Tools like RAGAS automate this with an LLM as the judge.
          
  
          
  
          Q16How do you keep the knowledge base up to date?+
          
    
          Give every chunk a stable ID (document + section) and store a version or updated-at date. When a document changes, delete its old chunks and re-ingest only that document. Schedule it, or trigger it from the system where the docs are edited.
          
  
          
  
          Q17How do you stop one customer from seeing internal or another customer's data?+
          
    
          Store access info as metadata on each chunk (tenant, role, city) and apply it as a filter inside the vector query, so forbidden chunks are never retrieved. Filtering after retrieval risks leaks and returns fewer results.
          
  
          
  
          Q18How do you reduce hallucinations in a RAG app?+
          
    
          • Tell the model to answer only from the context, and give it an exit ("I'll connect a human").
          • Ask for citations to chunk IDs or section numbers, so answers can be checked.
          • Use a low temperature and improve retrieval first, since a missing chunk forces a guess.
          • Measure faithfulness on a test set.
